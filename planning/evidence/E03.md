# E03 evidence — export UI and routing

Status: **READY FOR REVIEW**. Task: E03. Base: `5aa0002` (E02 branch tip). Branch:
`task/E03-export-ui`. Covers E3–E7 end to end (UI half).

Adds the keyboard binding, the message-menu row, and the routing that carries
one message's owning account to `mail.exportEml`. The bytes and the write are
E01/E02's; nothing here writes a file or reassembles mail.

## Keyboard binding

`Ctrl+Shift+S` — chosen by the owner — in the `list` and `reader` contexts, added
to `ui/keys/Keymap.js` (the one binding table) as `exportEml`. It therefore
appears in the shortcut sheet and is asserted against `docs/KEYS.md` by
`ui/tests/test_keymap.js`. It is **not** given a status-bar hint: that row is
curated (star has none either), and `Ctrl+Shift+S` matches Thunderbird/Gmail's
"Save as" rather than sitting beside archive.

`App.qml` answers it with one line, because the file sits 144 bytes under the
repository's 128 KiB per-file ceiling:

```qml
if (id === "exportEml") return service ? service.exportFromView(currentView, cursorId) : false
```

`Service.exportFromView(view, cursorId)` resolves the reader's open message
first, else the list cursor, so the resolution lives with the routing rather
than in the view.

## Routing and availability

- **Owning account, not the active one.** `Service.exportEml(id)` uses the same
  `hostForId`/`sourceIdFor` pair every other message action uses, so a unified
  list and a conversation-rail member both resolve to the account and native id
  that own the message. The `mail.exportEml` call receives that account id.
- **Menu path.** `MessageMenu` gains a `Save as .eml` row and calls
  `service.exportEml(id)` directly, as `Open in browser` already does; the row is
  hidden unless `service.canExportEmlFor(id)`.
- **Availability is two facts.** `Service.backendCanExportEml` reads the
  backend's advertised method list from the handshake (`protocolInfo.methods`,
  which `test_backend_api.py` already asserts), and `MailAccount.canExportEml`
  reads the provider's `emlExport` capability. Both must hold; Gmail/Hey/JMAP and
  a stock backend without the method are refused, with the refusal named in the
  mailbox notice rather than an empty list.
- **One request per mailbox at a time**, guarded by `MailAccount.exportingEml`.
- **Result and errors.** Success calls the mailbox `note("Saved <filename> to
  <path>")`; a failure calls `fail(message)`. Success is reported only from the
  returned result, so there is no false success after a timeout. Read state and
  selection are untouched — the call changes no flags and moves no cursor.

## Not verified here

- A live end-to-end export (needs a configured IMAP/Outlook account and a real
  server); the backend path itself is covered by E01/E02 tests.
- Busy/success/error screenshots: they require a live account, so none are
  attached. The busy state is the mailbox notice plus the duplicate-request
  guard; there is no modal.
- The conversation-rail member path is routed by the same `hostForId`/`sourceIdFor`
  as rows, but the member-specific UI test is not written yet.
