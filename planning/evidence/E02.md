## Behaviour

- **Account**: `account` is required. Empty, unknown, control-bearing, or
  over-long ids are refused with `mail_account_unknown` **before any credential
  lookup or socket**; the active account is never substituted.
- **Provider**: only `outlook` and `imap` are supported, checked against the
  `emlExport` capability and the account's refusals. Gmail/Hey/JMAP →
  `mail_export_unsupported` with no fetch and no file.
- **Message id**: `<uid>:<folder>` is validated before provider work.
- **Bytes**: taken from E01's `imap.rawMessage` (`EXAMINE` + `BODY.PEEK[]`, one
  literal, unsolicited UIDs ignored) and written unchanged.
- **Limit**: 25 MiB. The base64 length is checked before decoding, then the
  decoded length is checked again.
- **Filename**: built from the untrusted `suggestedName` — basename only,
  controls/separators dropped, capped to 240 bytes, `.eml` appended once,
  `message.eml` fallback.
- **Write**: `create_dir_all(Downloads)`, then exclusive `create_new` with mode
  `0600` and `O_NOFOLLOW`; `write_all` + `sync_all`; the partial file is removed
  on any write/flush failure; collisions get ` (n)` rather than overwriting. On
  Windows the same is done through `platform::private_fs`.
- **Retained path**: the result carries the actual `path`, `filename`, and byte
  count after a committed write.
- **Cancellation**: observed before the file is created. Once the write commits,
  success is returned even if a cancellation arrives afterwards, so a committed
  file is never reported as a failure.

## Tests (focused)

`src/mail/export.rs` unit tests: safe/one-`.eml` filenames (Unicode, empty, `..`,
control, path-like, over-long); duplicate names never overwrite; a symlink target
is never followed and the new file is mode `0600`; a missing/`invalid` base64
payload is `mail_export_incomplete`; an over-limit payload is refused before
decoding; a committed export reports the exact path/filename/bytes with matching
file contents; an unsupported provider is refused with the directory untouched.

`src/backend/mail_action_tests.rs` and the REST of the suite stay green; the
contract runner executes the new unreleased case.

## Security verdict

Scope: the new backend export path, on Linux, exercised by the tests above.

- **Account/identity confusion** — PASS. Strict, explicit resolution; no active
  fallback; unsupported providers refused before any fetch.
- **Filesystem** — PASS (Unix). Exclusive creation, `0600`, `O_NOFOLLOW`, no
  overwrite, partial cleanup on failure; symlink target untouched. Windows path
  uses the platform primitives but is **NOT VERIFIED** at runtime here.
- **Resource bounds** — PASS. 25 MiB checked before decoding and again after;
  the transport stays capped at its existing 32 MiB response bound and the
  operation does not raise any global limit.
- **Secret handling** — PASS. Credentials are resolved inside the IMAP layer as
  for every other provider call; none is logged, returned, or placed in the
  result. The result carries only ids, path, filename, and byte count.
- **Partial files** — PASS. No partial `.eml` survives a write failure; a
  committed file is never reported as a failure.
- **Not verified**: a real 25 MiB message over a live server, macOS/Windows
  runtime, and live-account export (requires credentials and is out of scope).

Claim: the desktop export path is PASS for the tested boundaries; cross-platform
runtime is NOT VERIFIED.
